# Review 2026-08-21 — verifying the remediation

A second pass over the whole repo, two days after [[Review 2026-08-19]] and the
work in [[Remediation Log]]. The question this time was not *"what is wrong
with the project"* but *"did the remediation actually hold, or was it rushed?"*
— prompted by a long red streak in CI during the work and a general sense that
too much had changed too fast.

## Short answer

**The remediation holds.** Every critical fix was verified in the code rather
than taken from the log:

| claim | verified |
|---|---|
| F04/F05 — thread-safe, incremental scoring | `threading.RLock` on every path that touches `flows`; `window` bounds both host context and the returned rows; dirty-flag watermark. The demo reports `scored=16,546 reused=266,146 (94% cached)` |
| F03/F18 — export parity guards | `train_live_model.py`, `02_train_sfaf.py` and `export_c.py` all compare against the source model and `sys.exit` (and `os.remove` the artifact) below 0.999 |
| F06/F07 — IPS scope and idempotence | explicit `host`/`network` scope with FORWARD chains; `nft flush table` before declaring, so restarts cannot accumulate rules |
| F10 — dashboard | defaults to 127.0.0.1; a non-loopback bind *requires* a token; `hmac.compare_digest` |
| pickles removed from git | `git ls-files | grep -c '\.pkl$'` → 0 |

CI on the branch tip is **green** (both the push and the PR run). The red streak
was the middle of the work, not its end state.

## What the second pass found anyway

Four new findings, none of which invalidate a research conclusion, two of which
would have bitten on real hardware.

- [[F20 - FlowTable generation map grows without bound]] — *significant.* The
  sensor's only memory bound cleans two of its three maps. Demonstrated: 20k
  connections, flows back to 0, generation map holds all 20,000 forever.
  Introduced **by** the F16 teardown fix.
- [[F22 - Benchmark published a report with a hole in it]] — *significant.* A
  catch-all `except` reported a `ValueError` as `(section skipped — ...)` and
  published it. The committed BENCHMARK.md had been carrying the evidence for a
  day. Also found: two hardcoded cross-dataset figures still quoting the
  ten-dataset run.
- [[F23 - Retracted thesis numbers still shipped as current]] — *significant.*
  25 pre-remediation artifacts still tracked and unmarked, including a file
  titled "Key Numbers for Report" containing the retracted +56.59 pp claim.
- [[F21 - Dataset entry point dies on an unmounted drive]] — *moderate.* The
  README's first command dies with a traceback when the external drive is
  unplugged, and the test covering it was not hermetic.

## The pattern in all four

Three of the four are **the remediation's own footprint**:

- F20 is new state added by a correctness fix, never wired into the lifecycle
  that bounds it.
- F22 is a signature change (`read_pcap` gaining `orig_len`) with one caller
  left behind, hidden by a catch-all.
- F23 is a correction that produced new numbers without retiring the old ones.

This is the honest cost of a large remediation pass, and it is a specific,
checkable cost rather than a vague "it was rushed". A fix's new state, its
callers, and its superseded outputs each need the same attention as its logic.

F22 is the sharpest instance, because the [[Remediation Log]] had *already*
written the rule — *"make the check able to fail, not merely able to print"* —
one day before a catch-all `except` in the benchmark was found doing exactly
that. Knowing a failure mode is not the same as being immune to it, which is
the same course correction the threshold-transfer script needed.

## What changed as a result

Fixes and their regression tests, plus three things that make this class of
failure structural rather than attentional:

- **A linter in CI.** `ruff check .`, pyflakes rules only. F22 was found by
  `F821 Undefined name` — a guaranteed `NameError` on a reachable line, not a
  style preference. Style rules are deliberately off; the codebase has a
  hand-laid format an autoformatter would flatten.
- **The benchmark exits non-zero** if any section failed, and CI greps the
  published report for `section FAILED`.
- **CI asserts its own hermeticity** — no `Datasets/` in the checkout, no
  `/Volumes/` path in tracked code — so the suite cannot drift back to
  depending on one machine's hardware.
- `concurrency: cancel-in-progress`, so a rapid series of pushes stops running
  a full matrix per push.

Suite: **40 → 45 checks**, 12 seconds, all passing. Lint clean. Demo exits 0.

## Still open

Nothing new. The roadmap is unchanged and [[Future Work]] item 1 remains the
one that matters: **the live model has never seen real labelled traffic.**
Every number for the live half is a property of the synthetic generators, and
the IoT-23 pcaps to fix that are now available on the mounted drive.
